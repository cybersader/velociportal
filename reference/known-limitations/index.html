    Known Limitations¶

    This page describes the current implementation and approved deployment boundary, not the long-term design. One process selects either Headscale or Tailscale SaaS. Headscale is the supported implementation path; Tailscale SaaS is a labeled preview until live acceptance passes.

    Policy support¶

    • Headscale remains legacy-ACL-only. Headscale uses legacy_acl_visibility_v1 and evaluates acls entries with action: "accept".
    • Tailscale Grants support is narrow. Tailscale reports network_access_visibility_v1 when accepted Grants participate. ACLs and Grants are additive, but only network src/dst/ip semantics are modeled. Posture, IP sets, services, non-empty via, application capabilities, malformed capabilities, and unknown semantics reject the refresh.
    • Port/protocol precision differs by rule kind. Legacy ACL destination ports are stripped and protocol fields remain unmodeled, so ACL-derived visibility can overstate a port-specific rule. Grant-derived visibility requires a capability that permits TCP to the exact NPM forward_port; valid UDP/ICMP/non-TCP-only Grants load but produce no HTTP card.
    • Machine sources never become browser identities. Valid source tags, IPs, CIDRs, host aliases, autogroup:tagged, autogroup:shared, and other machine selectors may load so machine rules do not block a Tailscale snapshot, but they never match a human request. tagOwners and tags on owned nodes do not make a human a tag:* source. Destination tags still resolve through node addresses.
    • Role membership uses Tailscale's explicit automatic memberships only. Supported human-role autogroups become browser evidence only for Grants and the bounded SSH Machines projection, through the authoritative Users API mapping. A direct type: "member" user receives autogroup:member plus its API role; the Owner additionally receives autogroup:admin. A type: "shared" user receives none, and specialized roles do not imply one another. Membership requires exact canonical loginName equality; padded API logins reject the complete refresh. Membership is never inferred from devices, owners, tags, or tagOwners. Legacy ACLs and nodeAttrs do not consume this mapping.
    • Node attributes do not authorize. Attr-only Tailscale nodeAttrs may load only for *, individual users, defined groups, tags, and autogroup:member targets with the funnel attribute; they never grant a card. Unknown attributes, malformed section types, and non-empty node-attribute application capabilities fail closed.
    • autogroup:internet fails closed. It is not treated as a wildcard.
    • Empty policy means zero cards; unsupported policy blocks refresh. Empty access-rule sections are a complete zero-card snapshot. A non-empty unsupported construct rejects the new snapshot; a warm process retains the exact previous snapshot and a cold process remains without one.

    SSH Machines preview¶

    • Machines are a separate Tailscale-only visibility projection. The complete section is rendered only when Tailscale is selected and the ssh section is present and fully supported. Headscale, absent SSH, and unsupported SSH omit the section. When the projection is available but the current identity has no matches, the portal retains an explicit empty Machines state. SSH rules do not authorize HTTP service cards, and NPM proxy hosts do not authorize machines.
    • Two independent policy matches are required. The exact direct member must match both one supported Tailscale ssh rule and one network Grant that permits TCP/22 to the same device. A legacy ACL mentioning port 22 is never sufficient. Service metadata, NPM access lists, and health observations are not inputs.
    • The supported SSH subset is intentionally narrow. Sources are exact full logins, defined groups containing only exact full logins, or supported human-role autogroups. Destinations are tags or autogroup:self. Actions are accept or check; users are validated literal account names or autogroup:nonroot; an optional canonical checkPeriod is accepted only for check from one minute through 168 hours. Local-part mappings, wildcard users, machine sources, IP/CIDR destinations, unknown fields/actions/selectors, malformed shapes, and out-of-range periods make the SSH section unsupported and therefore unavailable for rendering.
    • Unavailable SSH projection does not broaden or invalidate HTTP cards. One unsupported SSH rule marks the whole SSH section unsupported and omits the Machines section, while otherwise supported ACL/Grant service matching and the complete snapshot remain available. Doctor preserves the top-level coarse unsupported state/reason/rule diagnostic but emits per-identity machine previews only when the projection is available.
    • Only authoritative direct members can receive machines. Shared users receive no role membership or machines. Exact login, group, role, Owner-to-Admin, specialized-role isolation, destination, and autogroup:self behavior use the same strict Users/device inputs as the Tailscale adapter; tags and tagOwners never turn a machine selector into a human.
    • Machine rows are not connection or enforcement proof. The compact list requires SSH policy, Grant TCP/22, and exact current device sshEnabled=true plus blocksIncomingConnections=false evidence, then prioritizes choosing an account and copying a Tailscale SSH command. Exact account scopes and identity-check behavior remain available under collapsed Policy details. Tailscale SSH and the destination OS still enforce the session, account, check flow, device state, and reachability.
    • A short display/search name is derived only from the already validated canonical target. For a canonical *.ts.net device, the card prominently shows its first DNS label (for example server from server.tailnet.ts.net) alongside the full canonical name in smaller muted text; a validated IP fallback target has no separate short form and is shown once. The short name is never a separate discovery input -- it is always re-derived from the same target the matcher already validated, never from raw node hostnames or hostname-suggestion candidates.
    • Action labels are truthful, plain-language SSH policy text, not raw policy tokens. An accept rule reads "No extra sign-in"; a check rule reads "Reauthenticate every <period>", using the exact canonical checkPeriod when present or Tailscale's documented 12-hour default when it is absent. These labels describe Tailscale's identity check, never machine health or account existence.
    • Copy commands are deliberately narrower than displayed policy. A literal-account command is offered only for a validated literal account and is built entirely server-side. autogroup:nonroot remains a human-readable policy summary because it does not identify one account, but where it applies the portal additionally offers a safe, purely client-side text input: the viewer may type a candidate account name, which is validated in the browser against the same bounded grammar as literal accounts (also rejecting root outright, since that account is never part of the autogroup:nonroot scope) before a command is built and copied. Velociportal never verifies that a typed account exists on the machine and the input is never sent to or rendered server-side. The command target is always the canonical full *.ts.net device name or, for IP-fallback targets, a validated Tailscale CGNAT IPv4/Tailscale ULA IPv6 address -- the same server-validated value already used for the card and console link. Arbitrary FQDNs, ordinary private addresses, single-label names, shell metacharacters, and invalid accounts never become copied commands.
    • Machine evidence is not yet in validation schema v3. Doctor can preview only the triple-evidence machine count and deliberately omits device IDs, names, addresses, accounts, capability values, and commands. Operators must compare the portal rows and copied commands against live Tailscale SSH behavior for at least two identities before treating the projection as useful evidence.
    • Tailscale provides no standalone browser-SSH session URL. Velociportal can only navigate to the fixed admin-console Machines page. Every rendered machine requires exact device sshEnabled=true plus blocksIncomingConnections=false from /devices?fields=all; missing, null, malformed, disabled, incoming-blocked, or mismatched values fail closed and remove the machine. The navigation action additionally requires a direct member holding an automatic-admin-equivalent role (Owner, Admin, IT admin, or Network admin). Its query uses the validated short canonical name or IP plus property:tailscale-ssh, and opens in a new tab. Device capability narrows the projection but remains current self-report, not authorization, health, reachability, or proof that a browser session will succeed. Tailscale remains responsible for console eligibility, reauthentication, SSH policy, device posture, account choice, and the session itself.

    Service matching¶

    • The join uses NPM forward_host. Supported destinations include exact hosts/IPs, CIDRs, policy aliases, destination tags resolved to node IPs, *, and autogroup:self.
    • The join is not proven against a real deployment. NPM may store a Docker name while Headscale resolves an IP or tag. A matching RFC1918 address also requires an advertised, approved, and client-accepted subnet route.
    • NPM access lists are not visibility inputs. access_list_id is not used to decide cards.
    • Automatic card URLs reuse NPM's backend scheme. An HTTPS frontend with an HTTP backend can produce an incorrect http:// card. Add an explicit service-metadata URL when the public browser scheme differs.
    • Only one concrete NPM domain becomes the automatic card link. Velociportal selects the first valid concrete domain, even when a wildcard appears earlier. Additional domains are not rendered separately.
    • Wildcard-only services are visible but unlinked. Add the real concrete hostname to the same NPM proxy host when possible; otherwise use the strict service-metadata overlay. Velociportal never turns *.example.com into a %2A link and never silently drops an otherwise authorized service.
    • Presentation metadata is not discovery or authorization. Overrides are keyed by an existing NPM proxy-host ID. Version 1 can change only the displayed name or browser URL; version 2 may also assign a category and integer order. Category/order group and sort only the already-authorized cards: uncategorized cards remain last, explicit order applies within a category, and deterministic name/ID fallbacks remain. Metadata cannot create, hide, or enable cards, repair a missing NPM domain, change the policy join, alter health, or prove reachability.
    • Hostname suggestions are one-shot proposals, not discovery. suggest-hostnames uses only node/device names already returned by the selected provider plus optional bounded hostname-only stdin. Provider-visible names may be controlled by enrolled devices and are not proof of association with an NPM backend; the operator must verify every destination before merging. The command does not scan DNS, read resolver/NPM logs, infer short-name suffixes, persist candidates, mutate active metadata, or add authorization evidence.
    • Ambiguity fails closed by complete graph component. A proposal is emitted only when one canonical hostname maps to exactly one eligible wildcard-only NPM proxy-host ID. One-to-many, many-to-one, and chained conflicts are excluded in full; source preference, suffix length, input order, IDs, addresses, and first-seen order never break ties.
    • Backend health is explicit opt-in and observational. NPM meta.nginx_online remains route/configuration state and is never used as backend health. Only proxy-host IDs in the strict service-health file are probed, and only reachable is shown in green.
    • Probe targets are NPM backends, not browser URLs. HTTP/TCP targets derive only from forward_scheme, forward_host, and forward_port; presentation-metadata URLs are never probed. HTTP uses GET with an explicit path/status policy, while TCP connects and closes without sending payload data.
    • Topology allowlists are mandatory but not proof of safety or reachability. Every resolved address must fall inside an explicit CIDR, DNS names must also match an exact host or suffix, and loopback/unspecified/multicast/link-local/broadcast plus selected control-plane/NPM API sockets remain denied. DNS answers are validated as a complete set and dialed by validated IP, but operator-supplied CIDRs and DNS remain deployment trust inputs.
    • Health is shared and non-authorizing. Observations are memory-only, have no history, become stale after three configured intervals, and are joined only after identity/policy matching. They never create, hide, enable, reorder, or authorize cards and never affect /healthz.
    • Personalization is per-identity, browser-local, and intentionally narrow. A username-triggered accessible settings panel holds the one preference: hiding or showing the fixed built-in Velociportal logo. The mobile More control opens the same panel as a bottom sheet. The preference is scoped by an opaque SHA-256 digest of the exact login (never the raw login) and stored only in that browser's localStorage; a legacy unscoped key migrates once into the scoped key. It is never sent to or stored by Velociportal. Optional strict PORTAL_LOGO_DEFAULT=visible|hidden supplies only the initial deployment default applied when no valid browser preference exists for that identity; the per-identity browser choice always wins once set. Velociportal does not accept arbitrary per-service logos, collect access history, or provide server-side/account-synchronized personalization or delegated administration.
    • The PWA shell is install metadata, not an offline portal. Identity-derived portal responses are marked no-store, and the service worker has install/activate lifecycle handling only: no fetch interception, Cache Storage, offline fallback, or cached cards. Full service-worker control and normal install prompts require HTTPS or localhost. The canonical plain-HTTP Tailscale Serve route does not provide a secure context, though a browser may still allow a basic home-screen shortcut. HTTPS Serve/private TLS is a separate infrastructure decision.

    Provider selection and credentials¶

    • One provider per process. CONTROL_PLANE=headscale|tailscale selects one tailnet source. Multi-tailnet aggregation is not implemented.
    • Implicit Headscale is temporary compatibility. An absent selector defaults to Headscale only for the v0.2 line and emits a value-free warning. Explicit selection becomes mandatory in v0.3.
    • Inactive known credentials are ignored. Runtime warns only by variable name. Doctor and validation include active and inactive known credential material in redaction inputs. The setup wizard requires confirmation before deleting inactive known keys during a provider switch and leaves the file byte-for-byte unchanged on refusal or input abort.
    • Tailscale is OAuth-only. There is no API-key fallback, access-token variable, configurable API origin, or explicit tailnet variable. The OAuth credential's - alias selects the tailnet.
    • Tailscale remains preview. Immutable v0.2.0-rc.12 is the last independently confirmed running image at sha256:370a2d2b70ee58e12c403f71a5f78056476ed45913814563a115fa302d1fa288; live TrueNAS environment files reference it, and live rendering confirmed the compact machine list but exposed inconsistent action columns, non-SSH devices receiving policy-only copy controls, and service-health labels squeezing service domains. v0.2.0-rc.13 is tagged on main fixing those problems -- explicit device SSH capability is now required for every machine card, row actions are aligned, and service names wrap on a full line -- but has not yet been published as an immutable image or exercised live. A separate unpublished branch built on RC.13 adds mobile shell redesign, persistent browser-only search, and backend-check-scoped service-status wording. Token refresh/revocation, separate owner mapping, two-identity service and machine parity, unsupported-policy/SSH negatives, copied-target parity, and actual HTTP/SSH reachability still require live proof.

    Runtime upstream transport¶

    • Headscale HTTP is narrowly allowlisted. Configuration accepts HTTP only for exact local/internal host forms implemented by the validator. The canonical production value is http://headscale.velociportal.internal:8080. Other locations require verified HTTPS.
    • The allowlist does not prove confinement. It cannot prove that velociportal-upstreams exists, that the alias identifies the intended container, that port 8080 is not published elsewhere, that direct routing is absent, or that untrusted containers cannot join the bridge. Those are deployment acceptance requirements.
    • NPM HTTP is narrowly allowlisted and topology-dependent. Canonical runtime NPM traffic uses http://npm.velociportal.internal:81; only that exact alias and same-host/loopback compatibility routes may use HTTP. Every other NPM location requires verified HTTPS. The hostname check still cannot prove the deployed route is private.
    • Credentialed clients refuse redirects and environment proxies. All provider and NPM transports bound response headers/bodies. HTTPS uses normal verification and TLS 1.2 or newer. There is no insecure TLS mode.
    • Tailscale uses one fixed origin. Production calls only https://api.tailscale.com/api/v2, keeps OAuth access tokens in memory, refreshes early, and retries once after 401. The adapter rejects responses that advertise pagination or partial users/devices data.
    • Users and device mapping are intentionally strict. The complete Users API response must contain canonical exact IDs, unpadded loginName, type, and role values before Grant/SSH-machine role membership is derived. Device-owner resolution remains a separate mapping; blank, duplicate, ambiguous, malformed, padded, or unresolved data rejects the refresh. Tagged devices may omit a human owner; untagged devices may not. Neither mapping infers the other.
    • The private bridge is egress-capable by design. TrueNAS catalog apps replace their implicit default network when any UI-managed network is selected, so NPM and, in Headscale mode, Headscale require velociportal-upstreams to provide outbound NAT and Docker DNS. Tailscale SaaS API traffic uses the preferred default network. A normal user-defined bridge does not publish ports to the LAN, but host or privileged workloads remain within the deployment trust boundary.
    • The base production stack has no CA mount. The optional private-CA overlay mounts only a readable public root for verified-HTTPS alternatives. Never mount a CA private key or leaf private key.

    NPM Headscale control proxy¶

    This section applies only when CONTROL_PLANE=headscale. Tailscale SaaS mode still reads NPM proxy hosts but does not require Headscale, headscale-ops, or the NPM Headscale control proxy.

    • NPM is a trust and availability boundary. Existing NPM terminates the trusted Headscale HTTPS origin required by brand-new clients and HTTPS-only headscale-ops, then forwards to privately addressed Headscale HTTP.
    • NPM can observe control traffic and operator Bearer API keys. Keep operator and Velociportal runtime keys separate. Runtime Velociportal bypasses NPM.
    • Protocol preservation requires live proof. WebSocket and HTTP upgrade behavior must be enabled and tested against the real Headscale version.
    • Logging posture requires live proof. Custom NPM logs must not record Authorization or full request headers.
    • NPM backup/restore is part of Headscale availability. Database, configuration, certificates, and automated renewal state require tested backups.
    • Pre-tailnet certificate trust is mandatory. The privacy-preserving canonical form uses split-horizon/private DNS plus an existing publicly trusted wildcard certificate from the operator's automated DNS-01 NPM lifecycle. Do not publish the Headscale hostname/address in public DNS or issue an exact-host public leaf certificate that exposes it in certificate-transparency logs. If a required joining client does not already trust it, stop rather than disabling verification.

    Identity and browser ingress¶

    • Only Tailscale-User-* headers are supported. Tailscale-User-Login is required. Authentik, Authelia, Remote-User, and X-Webauth-* are not accepted.
    • Full-domain identities match exactly. A trusted alice@example.com login does not inherit ambiguous alice@ or bare alice membership. Grant/SSH-machine role lookup also requires the exact canonical Users API loginName; short, bare, cross-domain, case-variant, and padded API identities do not inherit role membership.
    • The immediate source must be trusted. Requests outside TRUSTED_PROXY_CIDR are rejected. Broad Docker, LAN, or tailnet CIDRs weaken spoofing resistance.
    • Host-loopback topology requires Docker Engine 28+. Older engines may expose localhost-published ports to same-L2 hosts. Host processes and host-network containers that can reach loopback may share the trusted Docker-gateway source.
    • Human Serve identity only. Tagged-device and Funnel requests do not receive user identity headers.
    • Tailnet HTTP Serve is canonical. The browser origin is HTTP on port 8081, but ordinary on-path LAN/router/ISP observers see WireGuard-protected transport. Endpoint, host, NPM, Tailscale/Headscale control-plane, and trusted-workload compromise remain in scope.
    • Headscale automatic HTTPS Serve remains future work. Official Tailscale can automate *.ts.net certificates. Track Headscale issue #2527 and PR #3300. Tailnet HTTP Serve is not a release blocker.
    • NPM is not portal identity. An NPM route cannot derive the caller's human Tailscale identity.

    Deployment and operations¶

    • Production requires Docker Compose 2.33.1+ and Docker Engine 28+. Raw env-file parsing, explicit network gateway priority, and safe localhost publication depend on those versions.
    • Production always consults the registry. pull_policy: always prevents silent reuse of a tagged local image, but operators must still record the resolved digest and never use latest.
    • Stack preflight is static, not deployment proof. doctor --stack-env catches malformed or mutable image references and inconsistent subnet/gateway/trusted-proxy values without credentials or network access, applying reported process-environment overrides with Compose precedence. It does not resolve a tag, verify registry publication or immutability, render every Compose overlay, inspect TrueNAS/Docker, or prove the actual trusted source.
    • Production and repository projects must remain distinct. Use a production project name other than the repository workflow's velociportal project.
    • No source build or recurring NAS shell is canonical. In Headscale mode, the one normal app-shell action is the first short-lived API-key bootstrap and routine administration is workstation-driven through HTTPS-only headscale-ops. Tailscale mode uses externally managed OAuth credentials and requires no Headscale shell.
    • No CA or durable application state belongs on the router. Router replacement restores ordinary DNS and routing only. Durable Headscale, NPM, policy, Serve, network, and Velociportal state stays on TrueNAS and backups.

    Validation status¶

    Schema-v3 validation reports record non-sensitive provider, policy-mode, support-level, explicit/implicit selection, access-rule counts, and rule_kind/rule_index provenance. They do not prove Docker confinement, identity injection, restart recovery, backup restore, join correctness, links, or per-user reachability.

    For Headscale, v0.1.0-rc.1 failed the first live TrueNAS network-attachment gate and was rolled back safely; v0.1.0-rc.2 corrects that topology but has not yet passed end-to-end acceptance. For Tailscale SaaS, immutable v0.2.0-rc.12 is the last independently confirmed running image referenced by the live environment files, but the exact running digest and private hostname-proposal exercise remain unverified. v0.2.0-rc.13 is tagged on main, requiring explicit device SSH capability for every machine card and fixing the row-action and service-name layout problems RC.12's live rendering exposed, but it has not yet been published or deployed. A separate unpublished branch built on RC.13 adds mobile shell redesign, persistent browser-only search, and backend-check-scoped service-status wording. Token refresh/revocation, separate owner mapping, unsupported HTTP-policy and SSH-suppression cases, two-identity service/machine isolation, copied-target parity, HTTP/SSH reachability, and live hostname-proposal acceptance remain unaccepted.

    No public support claim is warranted until the selected provider's live checklist plus at least two real identities, LAN-negative Velociportal access, restart persistence, every NPM join, every card link, and actual control-plane reachability have been checked. Use the real-deployment worksheet.
